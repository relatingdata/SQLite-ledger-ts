# Backend-First Testing

## The real testing pyramid, in order of preference

1. **Database level.** Raw SQL directly against the real schema — `INSERT`/`UPDATE` statements hitting real tables, checking that views and triggers (`localized_text`, `entity_delete`'s own `INSTEAD OF INSERT`, etc.) produce the right result. No TypeScript at all. The fastest, most isolated layer — and, confirmed directly this project's own real history, exactly where several real bugs actually lived (the `localized_text` view's own collision bugs, `createStockTake`'s whole-database name lookup).
2. **Backend function level.** Calling real `db.ts`/`db-stock.ts` functions directly (`createStockTake(...)`, `recordStockTakeCount(...)`) — no HTTP, no browser. Tests real business logic in isolation, in milliseconds.
3. **HTTP/API level.** Real requests against the real Express routes — tests the real request/response contract, auth, serialization.
4. **Browser/E2E level (Playwright).** Reserved for what is genuinely, irreducibly about the UI itself: layout, RTL mirroring, translation rendering, interactive widget behavior. Never the default reach for "verify a backend function works" — confirmed, directly, a real mistake made in this project's own history: a pure backend validation-error bug (a name-collision bug inside `createStockTake`) was first, wrongly, investigated via a Playwright browser test, adding real login flows, DOM selectors, dev-server timing, and duplicate-process risk — none of it relevant to a bug that a single, direct function call could have exposed in milliseconds.

## Before writing any new test

Ask, explicitly: **is this provably backend-only?** If a bug's own stack trace / error message names a backend file and function with no UI code in the path at all, it is backend-only — start at level 1 or 2, not level 4. Only escalate to Playwright when the specific thing being verified cannot be observed any other way (a real, visual rendering, or an interaction only expressible via real DOM events).

## Before running any Playwright test at all — a real, further, mandatory precondition, found directly from a real, confirmed failure

A hung or failing Playwright run can be caused by something that has nothing to do with the UI at all — the backend not actually responding, a stale server, a port conflict — and browser-level symptoms (a page that never loads, a step that never completes) look identical whether the real cause is a genuine UI bug or the server simply not being there. Confirmed directly, a real, costly mistake made in this project's own history: an extended, multi-attempt Playwright debugging session chased a "hung at this step" symptom for a long time before checking the single, most basic thing — a raw `curl` against the backend's own login endpoint — which immediately, unambiguously showed the real server was not responding at all (`000`, connection refused), something no amount of browser-level investigation could have diagnosed as fast.

**Mandatory, before launching any Playwright run, even one that looks purely UI-focused**: a raw, direct HTTP check against the backend (`curl -s -w "\nHTTP status: %{http_code}\n" ...` against the real login endpoint, or whichever real endpoint the scenario needs) confirming a real, correct response — not just a `/health`-style check, since a health endpoint can respond while a real, further endpoint (auth, a specific route) does not. This costs seconds and rules out an entire, real class of failure before spending minutes chasing it through a browser. If a business-creation or other data-shaped scenario is what's actually being tested, run that same real data through the backend API directly first (the same real principle as the shared-fixtures rule below) and confirm a correct result before ever pointing Playwright at it — never assume the backend will accept the data just because the test script was written to send it.

### A real, explicit skill-review-after-failure, applied here directly

Per `skill-skill-review-after-failure`'s own, mandatory process, not skipped:

1. **The real, hidden assumption**: that an earlier, successful `/health` check meant the backend stayed genuinely healthy and reachable for the rest of the session — health can change between any two checks, and a lightweight health endpoint responding says nothing about whether a real, further endpoint (login, a specific route) does.
2. **Was this foreseeable?** Yes, completely — this skill already existed, already said exactly this, before the incident. This was not new information; it was an existing, known discipline not consistently applied under the pressure of a long, escalating debugging session.
3. **The real, honest impact of not following it**: a genuinely large amount of real time and real tool calls spent chasing a phantom "UI hang" — multiple full Playwright runs, repeated server restarts, and a broken, non-portable, OS-specific diagnostic script written and then discarded — every bit of which a single, five-second `curl` at the first sign of trouble would have ruled out immediately.
4. **Decision**: a revision to this existing skill (the paragraph immediately above), not a new, separate skill — the discipline already existed and was correct; what was missing was making "before *any* Playwright run" as absolute and unconditional as "before writing any new test" already was, so there is no space left to rationalize skipping it because a symptom "looks like" a UI bug.

## Shared ASCII fixtures across every level

When a single scenario or bug needs testing at more than one level (e.g. a schema-level repro, then a backend-level repro, then eventually a UI-level confirmation), every level reads the exact same, small, named, ASCII fixture — the same real discipline already established for this project's seed data (`shared-fixtures/*.csv`, read identically by backend scripts and Playwright tests). Never let each test level invent its own, separate, "similar enough" test data — that is exactly the kind of drift this project's own CSV migration work was created to eliminate for seed data, and the same principle applies to test fixtures.
