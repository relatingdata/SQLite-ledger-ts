# Specification-Driven Design

## The real, absolute rule

The manuals are the specification, not the write-up. **Nothing is implemented, and no test is written, except as a direct, traceable derivation of something the relevant manual already states.** If the manual doesn't yet state it, the manual is updated *first* — as its own, explicit step, visibly stated before any code or test is touched — and only then does work proceed from what it now says.

The real, required sequence, every time, for non-trivial work:

1. **State it in the manual.** The relevant manual (User Manual for user-facing behavior, Programmer's Manual for internal design/implementation/DB/API) is updated to say, explicitly, what the intended behavior is — before any test or code exists for it.
2. **Derive the test directly from that statement.** An e2e/Playwright test traces to a specific User Manual statement; a unit/API/DB test traces to a specific Programmer's Manual statement. Confirm the test genuinely fails first (per `test-driven-development`).
3. **Implement to make the derived test pass.** Not the other way around, and not from a mental model of what the feature "should" do — from what the manual, right now, actually says.

Deviating from this order — writing code before the spec is stated, or skipping the failing-test step — happens only when the user says so explicitly, in advance, for that specific piece of work, and why.

## Consulting the manual is a visible step, not a silent one

Per `manual-as-source-of-truth`: the Programmer's Manual (for internal/design/DB/API questions) or User Manual (for user-facing behavior questions) is checked *before* any exploratory `grep`/`view` against the live source, every time — not as a general habit, but as a step stated out loud, in the response or in visible reasoning, each time it happens: "checking the Programmer's Manual for X first." The same applies to the follow-up check of the manual's claim against the live code — that verification step is stated explicitly too, not folded silently into an answer as if it were simple recall. Both halves of this are worth surfacing because they're exactly the discipline that's easy to skip under time pressure, and skipping it silently is indistinguishable, to a reader, from never having done it at all.

## A divergence is reported, never resolved alone

The moment a real gap is found — the manual is silent on something the code does, or the manual and the live code actively disagree — that is a stop point, not a fix-it-and-move-on point. Report it directly: what the manual says (or that it says nothing), what the code actually does, and the two real, concrete options this implies — correct the code to match the manual's stated intent, or correct the manual to match the code's real, current behavior — each with what it would actually change and affect. Wait for the user's choice before touching either. This holds even when one direction seems obviously correct; which one is *intended* is a judgment only the user can make with certainty.

## The Programmer's Manual points to exact code, not just describes it

A Programmer's Manual entry that explains a mechanism without saying which function, in which file, implements it forces the next reader back into exploratory search — precisely the cost `manual-as-source-of-truth` exists to avoid. Going forward, a Programmer's Manual chapter describing a real, existing mechanism names the specific, real function(s) and file(s) that implement it directly (e.g. "see `getTrialBalance` in `backend/src/db-reports.ts`"), not just the mechanism in the abstract. This is a real, expected property of every chapter that documents already-built behavior, not an occasional nicety.

## A failing implementation is a stop point, never a debug loop — MANDATORY, per direct, explicit instruction after a real, confirmed violation

What actually happened, named exactly, so it is never repeated: asked to check whether currency exchange rates were genuinely exercised in the real simulation, a real, genuine gap was found correctly. Fixing it should have started with a design doc (a business's own real home currency; each real location/division nominating which real currencies it trades in; each nominated currency carrying its own real, independently-set selling price and COGS, per product and/or category) and a fully worked example of the resulting real journal entries, checked with the user, before any code. Instead: code was written directly into `completePosSale`, run against the real simulation, a real SQLite error read, the code patched to react to that specific error, run again, a *different* real error read, patched again — a live, unsupervised trial-and-error loop against a production mechanism, for several real iterations, with no specification existing anywhere to check the result against. A test was then written and edited, more than once, to match whatever the patched code's real output happened to be, rather than being derived from a stated specification and confirmed failing first. This is a real, confirmed, serious violation of both `test-driven-development` and this skill, not a stylistic shortcut.

**The rule, absolute, no exceptions without the user's specific, advance permission for that specific piece of work:**

- **A failing test, or a runtime error hit while extending an existing mechanism into new conceptual territory, is a hard stop — not a debugging opportunity.** The correct, only response is to stop writing code entirely and return to the manual: if the relevant statement doesn't exist there yet, write it — as its own real, visible step, before touching implementation again — and check the new code against it once it does. Never patch, rerun, read the next error, and patch again. If a second real error appears after a first attempted fix, that is not information to react to with a further patch — it is confirmation that no real specification exists yet and implementation must stop immediately until one does.
- **A test is never edited to match what code currently, actually does.** A test derives only from a specific, already-stated sentence in the relevant manual. If a written test disagrees with a running implementation, the implementation is wrong, the test is wrong, or the manual statement it derives from is wrong — which of the three is a real question for the user to answer, per "a divergence is reported, never resolved alone" above, never something to resolve by silently rewriting the test to agree with the code.
- **Before writing any implementation code that extends an existing, real mechanism (a function, a posting flow, an account-resolution rule) to handle a genuinely new concept it was never built for** (a new dimension of accounting treatment, a new kind of entity relationship, a new currency/quantity/tax rule) **- stop before the first line of code, not after the first error.** Check directly: does the relevant manual already state, in full, concrete detail (not "roughly" or "in spirit"), what the new behavior should be, including a fully worked example with exact account names and exact debit/credit amounts? If not, that is the immediate, sole task - write it, and wait for the user's confirmation on direction before implementing, exactly as any other real, non-trivial new feature already requires under this skill's own, existing, absolute rule above. Extending an existing function is not exempt from that rule merely because the function already exists.
- **A trial-and-error sequence against live output is the signal to stop, and naming it is not optional.** If a genuine third attempt at the same piece of code is about to be made without a written specification existing to check it against, that fact must be stated directly to the user *before* making that attempt, not folded silently into continued work.
- Deviating from any of the above happens only when the user says so explicitly, in advance, naming that specific piece of work and why - a general instruction to "continue" or "keep going" on a broader task is never, by itself, that permission.

## Why this exists

Per direct instruction, following a real, direct, immediate incident: a design already discussed and already documented (currency as a commodity, in `multicurrency-design.md`) was answered from scratch, by exploring the live code, without checking the manual first — producing an answer that was accurate about the *current, built* state but silent about the *already-decided, documented* design sitting one file away. The manual being the actual specification, checked first every time, with the check itself stated visibly, is the direct, permanent fix for this exact failure mode recurring.

A second, later, more severe incident directly prompted the stop-gate section above: asked to check a real, live gap (currency exchange rates never exercised against the real simulation), the fix was built by writing code directly, running it against real, live data, reading the real error it produced, patching in direct reaction to that one error, running again, reading a *different* real error, and patching again — genuine, unsupervised trial-and-error against a production accounting mechanism, several real iterations deep, with no written specification anywhere to check any of it against, and a test edited more than once to match whatever the code's real, current output happened to be. Per direct, explicit instruction after this was confirmed and named: every real change since the last clean checkpoint was reverted in full, and the stop-gate section above is the direct, mandatory, permanent answer to it — a failing test or a live runtime error is now, unconditionally, a stop point that returns to the manual, never a debug loop that reacts to the next error in sequence.
